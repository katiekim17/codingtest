# handoff — 코딩테스트 코치

## 문서 역할

| 문서 | 역할 |
|---|---|
| `.dryforge/spec.md` | 무엇을 만드는지(동작). 기준 문서. 다른 문서와 다르면 spec이 이긴다. spec을 고치려면 사용자 승인이 필요하다. |
| `.dryforge/plan.md` | 작업 순서와 대상 파일. 잠정안이라 자유롭게 고쳐도 된다. |
| `.dryforge/handoff.md` | 이 문서. 지켜야 할 선, 정할 때 오간 이유, 프로젝트 바탕. |
| 기존 코드 | 어떻게 하는지 참고만. 무엇을 할지의 근거가 아니다. |

## 실행 모양

새 기능 하나, 작업 5개, 차례 4번: T1 → (T2, T3 함께) → T4 → T5.

## 지켜야 할 선

- 코치는 5단계 전에 정답 코드를 주지 않고, 사용자가 "다음"이라고 할 때만 단계를 올린다.
- 커밋에는 코치가 쓰거나 옮긴 파일만 들어간다. 사용자가 따로 고치던 파일은 절대 섞지 않는다.
- 푸시 실패를 성공처럼 알리지 않는다.
- 예전 풀이 파일은 사용자가 그 문제를 다시 풀 때만 옮긴다. 일괄 정리하지 않는다.
- 기록 줄은 더하기만 한다. 지우거나 고치지 않는다.
- 다음 복습 날짜는 기록 줄에서 계산한 값과 항상 같아야 한다(같은 사실을 두 곳에서 따로 관리하지 않는다).
- 검사 명령 `python3 -m unittest discover -s tests`가 0으로 끝나야 각 작업이 끝난다. 테스트는 네트워크 없이 돌고 표준 라이브러리만 쓴다.

## 정할 때 오간 이유 (spec에 없는 것)

- 따로 앱을 만들지 않고 이 저장소 안 Claude Code 코치로 한 이유: 사용자가 한 명이고, 지금 구글·챗지피티로 하던 일을 그대로 대신하는 것이 목적이다. 2~3주 써 본 뒤 힌트 단계가 줄어드는지 보고 더 넓힐지 정한다.
- 날짜 계산을 대화가 아니라 스크립트로 맡긴 이유: 매번 Claude가 직접 계산하면 가끔 틀릴 수 있어, 사용자가 테스트로 확인할 수 있는 쪽을 골랐다.
- 확인 없이 푸시까지 하기로 한 것은 사용자가 고른 것이다(잔디를 바로 찍기 위해). 대신 범위를 코치 파일로 좁혔다.
- 걸린 시간에 쉬는 시간이 들어가는 것은 사용자가 단순함을 고른 결과다. 정밀하게 바꾸자고 "개선"하지 않는다.
- 유형 폴더 이름을 영어 소문자로만 둔 이유: 한글 폴더·파일 이름의 경로 문제를 피하려고.
- 점검 사이트를 릿코드로 한 것은 사용자가 고른 것이다(평소에 가장 많이 푸는 곳).

## 프로젝트 바탕 (실행하지 않는 맥락)

> go는 이 절을 맥락과 하네스 재료로 읽는다. 구현 대상이 아니다.

### 1. 프로젝트 정체

- 사용자 한 명이 코딩테스트 챌린지를 하며 푼 문제를 올리는 개인 GitHub 저장소다. 매일 푼 풀이를 main에 바로 커밋·푸시해 잔디를 찍는다.
- 지금 문제: 자주 막혀서 구글·챗지피티로 하나씩 물어 가며 이해하고, 무엇을 배웠는지가 남지 않는다.
- 이번에 만드는 것: 저장소 안에서 Claude Code로 부르는 코치. 서버·화면·데이터베이스 없음.
- 풀이 언어는 파이썬(설치된 버전 3.14). 사이트는 릿코드·프로그래머스·백준.
- 코치가 사용자에게 하는 말은 한국어로 한다.

### 2. 도메인 모델

- **문제**: 사이트 + 번호로 구별한다. 제목, 링크, 대표 유형(하나)과 추가 유형을 가진다. 저장소에 문제 하나당 풀이 파일 하나.
- **풀이 파일**: 머리말 + 코드. 자리는 `<사이트>/<대표 유형>/<번호>_<영어 이름>.py`. 다시 풀면 코드는 바뀌고 기록 줄은 쌓인다. 대표 유형이 바뀌면 파일이 옮겨진다. 지워지지 않는다.
- **예전 풀이 파일**: 머리말이 없거나 옛 이름 규칙인 파일(지금 저장소의 모든 파일). 계산에서 빠지고, 다시 풀 때 새 자리로 옮겨지며 그때부터 새 풀이 파일이 된다. 점검 문제를 고를 때는 "이미 푼 문제"로 친다.
- **시도(기록 줄)**: 날짜, 본 최고 힌트 단계(0~5), 걸린 분, 풀었음/못 풀었음, 점검이면 통과/미통과. 한 번 쓰면 바뀌지 않는다.
- **진행 중 문제**: 동시에 하나. 시작 시각과 본 최고 단계를 가진다. 끝나거나 그만두면 시도 하나가 되고 사라진다. 창을 닫아도 남아 있다가 다음에 이어 할지 묻는다.
- **힌트 단계**: 0~5, 사용자의 "다음"으로만 오른다.
- **다시 풀기 일정**: 시도 목록에서 계산되는 값(3 → 7 → 30일 → 끝, 실패 시 3일부터). 따로 저장하지 않는다.
- **점검**: 7일마다 권하는 실력 확인. 오래 점검 안 한 유형의 릿코드 새 문제. 힌트 0·30분 이내·풀었음이면 통과. 점검 중 힌트는 한 번 묻고 주면 미통과.
- **유형 목록**: 14개(spec 표). 사용자 승인으로만 늘어난다.
- **유형 노트**: 유형별 "이런 문장이면 이 유형". 코치 초안 + 사용자 확인으로만 늘어난다.
- **숫자 요약**: 시도 목록에서 계산. 유형별 최근 점검, 4주 주별 평균 힌트·평균 시간, 푼 문제 수.

### 3. 기술 결정 (사용자가 확인한 것)

- 형태: Claude Code 스킬(코치 설명서) + 표준 라이브러리만 쓰는 작은 파이썬 도구 + 단위 테스트.
- 저장: 기록은 풀이 파일 머리말에만 있다(유일한 기록). 진행 중 문제만 깃에 올리지 않는 로컬 파일.
- 문제 읽기: 링크를 읽고, 안 되면 붙여넣기.
- 코드 확인: 예제 입력으로 실제 실행.
- 올리기: 코치 파일만 한 커밋, 확인 없이 main에 푸시.
- 보안: 비밀값 없음. 외부로 나가는 것은 문제 링크 읽기와 GitHub 푸시뿐.
- 검사 명령: `python3 -m unittest discover -s tests`.

### 4. 앞으로 (이번 범위 밖)

- 예전 풀이 파일 일괄 정리(확장자 없는 파일, `leetcode/number_of_island`와 `leetcode/200_number_of_island` 중복 등). 사용자가 이번엔 빼기로 했다.
- 2~3주 사용 뒤 힌트 단계·점검 통과가 나아지는지 보고 기능을 넓힐지 정한다. 그 전에는 넓히지 않는다.
